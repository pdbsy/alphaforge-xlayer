## Reproduced gap XLQA-MANIFEST-01

At the imported baseline, `packages/chain-adapter/src/manifest.ts` types describe Robinhood only, but runtime validation merely compares document fields with the caller's expected fields. JavaScript/parsed external configuration can supply an unsupported pair to both sides; recomputing the document digest makes it pass. This violates the new migration specification's explicit supported-pair requirement. It is not evidence of remote exploitability: the expectation must originate in a trusted configuration path, and the imported composition still supplies a fixed Robinhood expectation.

03 source `6a2350f50852731c8a6433bcce0aa4e53c4f772c` validates the expected pair against the explicit allowlist before comparing document identity. All five negative tests and both positive controls pass at O. Trusted digest/address checks remain covered. Final integration must rerun them without changing expected outcomes.

## Reproduced gap XLQA-API-01

03 first reported the evidence-route gap, and the manager authorized its narrow production fix. QA independently reproduced it: with foreign-chain or foreign-vault operations already in the same database, the imported route checked only operation ID and owner and returned HTTP 200. This does not show that the submission API permits creating those records or that wallet authorization can be bypassed.

03 source `6a2350f` adds chain and target comparisons. At O every scenario first reads a normal record from the same DB successfully; foreign-chain, foreign-vault and foreign-owner records return HTTP 404 / CHAIN_OPERATION_NOT_FOUND. Both defects are closed for this exact local combination, not for an untested future integration.

## Integration protocol

Final combined runtime and C/R/S evidence must bind the actual manager integration SHA. The test uses no fetch/HTTP listener and all wallet/RPC providers are local in-memory fixtures.
